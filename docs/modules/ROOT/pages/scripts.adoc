= Scripts

This page documents the standalone scripts currently maintained in the `tools` repository.

[[eaf2csv]]
== `eaf2csv.py`

Converts ELAN `.eaf` files into tab-separated transcript CSV files.

Typical use cases:

* export time-aligned annotations into a simpler tabular format
* remap annotation IDs used by per-file YAML overlap exceptions

Key behaviors:

* rows are sorted by start time
* `id:N ` prefixes in annotation text are stripped from the exported `text`
* `ignore` pairs in YAML annotations are remapped to the new sequential `tu_id`

Example:

[source,bash]
----
python eaf2csv.py \
  --input-dir data/eaf \
  --annotations-dir data/annotations \
  -o data/csv
----

You can also convert explicit files:

[source,bash]
----
python eaf2csv.py \
  --input-files data/eaf/CONV001.eaf data/eaf/CONV002.eaf \
  -o data/csv
----

Output columns:

* `tu_id`
* `speaker`
* `start`
* `end`
* `duration`
* `text`

[[vert2eaf]]
== `vert2eaf` (`cli.py vert2eaf`)

Rebuilds `.eaf` files from corpus `.vert.tsv` files (`serialize.vert2eaf`). It replaces the former
`tsv2eaf.py`, which was removed because it read column names (`iu_id`, `iu_align`) that the current
`.vert.tsv` schema no longer has and knew nothing about translations.

Key behaviors:

* reads `Begin=` and `End=` values from the `align` column
* reconstructs enriched TU text from the token spans and prosodic links
* reattaches translations from `translations/<code>.translations.json` as ref-annotations when
  `--translations-dir` is given
* exits with an error if a transcription unit is missing `Begin=` or `End=`

[source,bash]
----
python cli.py vert2eaf --input-files tsv/BOA1007.vert.tsv --output-dir eaf/
python cli.py vert2eaf --input-dir tsv/ --output-dir eaf/ [--translations-dir translations/]
----

One `.eaf` is written per input file, named after the file stem (e.g. `BOA1007.eaf`). `sync.py --from-vert`
does the same for a single file, and also refreshes the linear files and the validation page.

== `vert2eaf-layered` (`tsv2eaf_layered.py`)

Converts a `.vert.tsv` into a *layered* `.eaf`: instead of one transcription
tier per speaker, it builds a hierarchy per speaker. Tier names follow the
Toolbox/ELAN interlinear `<code>@<speaker>` convention; the codes live in the
`_TIER_CODES` dict at the top of `tsv2eaf_layered.py`.

[cols="2,1,3"]
|===
| tier | ELAN stereotype | value

| `ref@<speaker>`
| time-alignable (top)
| unit id, time-aligned on the unit's `Begin=`/`End=`

| `ft@<speaker>`
| `Symbolic_Association` (under `ref@`)
| free translation of the unit, from `<name>.translations.json` (`--translations-dir`); matched by `parent_tu_id` → unit `tu_id`

| `tx@<speaker>`
| `Symbolic_Association` (under `ref@`)
| Enriched text of the unit (token `span`s joined, `=` on `ProsodicLink=Yes`)

| `tx_ortho@<speaker>`
| `Symbolic_Association` (under `ref@`)
| orthographic text of the unit (token `form`s joined)

| `tok@<speaker>`
| `Symbolic_Subdivision` (under `tx_ortho@`)
| one annotation per token, value = `form`

| `sent_id@<speaker>`
| `Symbolic_Association` (under `tok@`)
| syntactic-sentence id(s) of the token, from the `sent_id` column (space-separated when a token is in >1 sentence). Carries the many-to-many syntax↔TU relation: EAF is a tree, so this is a per-token label rather than a spanning tier — a sentence crossing TUs is the same id on tokens under different `ref@` parents. Emitted only when the column is present and non-empty.

| `nvb@<speaker>`
| `Symbolic_Association` (under `tok@`)
| for non-verbal / pause / unknown tokens only: `type` (+ `meta_label` when set)

| `lemma@` `pos@` `xpos@` `feats@` `dep@` `<speaker>`
| `Symbolic_Association` (under `tok@`)
| per-token linguistic annotation; only with `--linguistic`
|===

Empty leaf tiers are dropped: `ft@` when there are no translations, `nvb@` when
there are no non-verbal tokens, and any `--linguistic` tier whose column is `_`
for every token in the file.

NOTE: a `Time_Subdivision` unit tier would need a parent TU tier; with
`__units` as the top tier it is a plain time-alignable tier. Equivalent today,
since every TU holds exactly one unit.

[source,bash]
----
python -m cli vert2eaf-layered --input-dir tsv/ -o eaf_layered/
python -m cli vert2eaf-layered --input-files tsv/BOA1007.vert.tsv -o eaf_layered/ \
    -a audio/ --translations-dir translations/ --linguistic
----

Units missing `Begin=`/`End=` (or with non-positive duration) are logged and skipped.

=== Heterogeneous corpora and the `.etf` template

Files differ in which layers they carry: a POS-tagged conversation has `pos@` /
`lemma@` / `dep@`, an unparsed one does not; only some have translations. Each
`.eaf` keeps just the tiers it has data for (empty leaf tiers are pruned). This
is valid — ELAN never treats a missing dependent tier as an error — but the
folder is not uniform.

`--template PATH` writes an ELAN `.etf` alongside the run: the *full* tier set
(every layer, `sent_id@` included) for every speaker seen across the inputs,
plus all linguistic types and constraints. Two uses:

* **schema reference** — the template is the authoritative list of every tier,
  its stereotype and its parent.
* **make a folder uniform** — in ELAN, _File ▸ Multiple File Processing ▸ Add
  Tiers from an imported file_ (or _Edit ▸ Add New Tiers From Template_ per
  file) fills every `.eaf` up to the complete structure. Matching is by exact
  tier name, so the template must contain the real per-speaker names — it lists
  the union of all speakers and can get large for a whole module.

[source,bash]
----
python -m cli vert2eaf-layered --input-dir KIP/tsv/ -o KIP/eaf_layered/ \
    --linguistic --template KIP/eaf_layered/KIP.etf
----

== `linear2html.py`

Generates publication HTML pages and transcript PDFs from linearized transcript files.

Typical use case:

* write directly into the `KIParla-artifacts` repository layout
* keep shared `css/` and `js/` at repo root
* write per-module HTML pages to `MODULE/html/`
* write per-module PDFs to `MODULE/pdf/`

Example for `KIParla-artifacts`:

[source,bash]
----
python linear2html.py \
  --orthographic ../ParlaTO/linear-orthographic/PTA005.txt \
  --enriched ../ParlaTO/linear-enriched/PTA005.txt \
  --tsv ../ParlaTO/tsv/PTA005.vert.tsv \
  --conversations ../ParlaTO/metadata/conversations.tsv \
  --participants ../ParlaTO/metadata/participants.tsv \
  --artifacts-root ../KIParla-artifacts \
  --module ParlaTO
----

This writes:

* `../KIParla-artifacts/ParlaTO/html/PTA005.html`
* `../KIParla-artifacts/ParlaTO/pdf/PTA005-orthographic.pdf`
* `../KIParla-artifacts/ParlaTO/pdf/PTA005-enriched.pdf`
* shared assets under `../KIParla-artifacts/css/` and `../KIParla-artifacts/js/`

You can still pass `--output` explicitly if you want a custom HTML destination.

== `tsv2formats.py`

Generates two linear text outputs from `.vert.tsv` files:

* enriched linear transcription
* orthographic linear transcription

These outputs are used in downstream publication and maintenance workflows.

Example for a whole folder:

[source,bash]
----
python tsv2formats.py \
  --input tsv \
  --out_enriched linear-enriched \
  --out_orthographic linear-orthographic
----

Example for a single file:

[source,bash]
----
python tsv2formats.py --input tsv/CONV001.vert.tsv
----

Output shape:

* one `.txt` file per input `.vert.tsv`
* one transcription unit per line
* two columns per line: speaker code and linearized transcription

Important details:

* the enriched output keeps enriched spans, pauses, and error token punctuation
* the orthographic output strips non-alphabetic material from `error` tokens
* `unknown` tokens are rendered as repeated `x` characters in the orthographic output

This script is also invoked automatically by the `regenerate-derived` workflow
whenever TSV files are pushed to `dev`.
See xref:workflows.adoc#auto-regen[Automatic regeneration on TSV push].

== `merge_metadata.py`

Merges participant and conversation metadata from module repositories into the collection-level metadata tables.

Key behaviors:

* normalizes columns before merging
* fills missing target columns with empty values
* deduplicates by `code`, keeping the first occurrence

Example:

[source,bash]
----
python merge_metadata.py \
  --modules ../KIP ../KIPasti ../ParlaBO ../ParlaTO \
  --output-dir ../KIParla-collection/metadata
----

Expected module layout:

* each module path must contain `metadata/participants.tsv`
* each module path must contain `metadata/conversations.tsv`

Normalization currently handled by the script:

* in `KIP`, `school-region` is renamed to `birth-region`
* extra columns are dropped
* missing target columns are added as empty strings

== `make_patch.py`

Generates a unified diff `.patch` file from a lemmatization CSV, capturing transcription-level corrections to be applied back to a corpus `.vert.tsv`.

Typical use case: during lemmatization work, errors in the original transcription are spotted (wrong form, wrong enriched notation, wrong tokenisation).
This script extracts those corrections from the CSV and produces a patch that can be applied with `git apply` on the corpus module's `dev` branch.

What is patched:

* `span`, `form`, `jefferson_feats` — values are stripped of leading/trailing whitespace before comparison
* missing `speaker` / `tu_id` values are auto-filled when they can be inferred safely from CSV or neighboring tokens
* Token deletions — TSV tokens absent from the CSV are removed (e.g. the second half of a merged token); `Begin=`/`End=` alignment is transferred automatically to the neighboring token
* The recap is printed in row order and marks each change as `aggiunta`, `modifica`, or `eliminazione`

What is not patched:

* `lemma`, `upos` — annotation-only, not in source TSV
* `align`, `prolongations`, `pace`, `guesses`, `overlaps` — TSV-only columns; preserved from the original except for the automatic alignment transfer
* Annotation sub-token rows (numeric token id plus a letter suffix, e.g. `4-7a`)

Validation:

* every token must have non-empty `span` and `form` values in both CSV and TSV

Example:

[source,bash]
----
python make_patch.py \
  ../lemmatization-project/wip/KIP/BOA1007.csv \
  ../KIP/tsv/BOA1007.vert.tsv
----

Batch mode on a whole `wip` subfolder:

[source,bash]
----
python make_patch.py --batch ../lemmatization-project/wip/KIP
----

This scans all `*.csv` files in the folder and looks for the matching TSV in
`../KIP/tsv/<FILE>.vert.tsv`.
If the corpus repositories live elsewhere, pass the source root explicitly:

[source,bash]
----
python make_patch.py --batch ../lemmatization-project/wip/KIP /path/to/corpora-root
----

Output:

[source]
----
Patch written: ../lemmatization-project/patches/KIP/BOA1007.vert.tsv.patch  (+6 / -9 lines)
Recap written: ../lemmatization-project/patches/KIP/BOA1007.vert.tsv.recap.md  (3 items)
----

The output paths are inferred automatically from the CSV location (`wip/CORPUS/FILE.csv` → `patches/CORPUS/FILE.vert.tsv.patch`).
A custom output path can be passed as a third argument.

The `.recap.md` file lists every structural change (drops, alignment transfers, columns needing manual attention).
Check it before applying the patch.

To apply:

[source,bash]
----
cd /path/to/KIP
git checkout dev
git apply --check ../lemmatization-project/patches/KIP/BOA1007.vert.tsv.patch
git apply ../lemmatization-project/patches/KIP/BOA1007.vert.tsv.patch
git add tsv/BOA1007.vert.tsv
git commit -m "fix: transcription corrections from lemmatization of BOA1007"
----

See the lemmatization-project documentation for the full workflow, including how to handle recap warnings.

[[audio_check]]
== `audio_check.py`

Checks that the end of each transcript's last annotation is compatible with the length of its recording, to
spot problematic files (a wrong or swapped recording, an unfinished transcription, a time-shifted tier, a wrong
`duration` in `conversations.tsv`). It runs automatically inside `sync.py --from-eaf` and `cli.py process`, and
can be run on whole modules:

[source,bash]
----
python audio_check.py <module_dir> [<module_dir> ...] [--audio-dir DIR] [--all] [--update-summary]
----

The audio length is measured on `<DIR>/<code>.mp3` (or `.wav`, `.flac`, `.m4a`, `.ogg`, `.aac`) with `ffprobe` when
`--audio-dir` is given, otherwise it is read from `duration` in `metadata/conversations.tsv`; the result says which.
Two rules, both *warnings*:

* `AUDIO_OVERRUN`: the last annotation ends more than `max_overrun` (default 1 s) after the audio ends.
* `AUDIO_UNDERRUN`: the last annotation ends more than `max_underrun` (default 120 s) before the audio ends.

Thresholds live in the `audio_check` block of `configs/defaults.yml` (override per module; `enabled: false` turns the
check off). With metadata as the source, `max_overrun` is widened by `metadata_slack` (60 s) because durations are
often rounded to the minute. `--update-summary` writes the results into the module's `tmp/process/json/summary.json`
so the *Audio length* section of the validation page can be refreshed without reprocessing.

[[check_participants]]
== `check_participants.py`

Cross-checks each conversation's `metadata/conversations.tsv` `participants` list against the actual `speaker` values found in its `tsv/<code>.vert.tsv`, flags transcript speakers with no row in `metadata/participants.tsv`, and cross-checks `conversations.tsv` `participants` against `participants.tsv` `conversations` in both directions.

Known non-participant placeholder tiers (`?`/`??`/`???`, `environment`, and the older names `commenti`, `suoni`, `sottofondo`, `gruppo`, `video`, `trad_video`) are excluded so real mismatches aren't buried in noise.

[source,bash]
----
python check_participants.py                          # auto-discover all modules
python check_participants.py --modules ../KIP ../ParlaBO
----

Pass `--add-unknown-participant-column` to add/refresh an `unknown-participant` column in each module's `conversations.tsv`, `yes`/`no` depending on whether the conversation's transcript contains a placeholder speaker tier:

[source,bash]
----
python check_participants.py --add-unknown-participant-column
----

[[generate_validation_report]]
== `generate_validation_report.py`

Builds one validation page per module (plus an index), combining `check_participants.py`'s metadata-consistency results with per-conversation pipeline warnings/errors from each module's `tmp/process/json/summary.json` (produced by `cli.py process`):

* xref:validation.adoc[Validation] — index of all modules, with per-module counts. Each module has its own page, `validation-<module>.adoc`, with two sections:
** *Errors* — an interactive, filterable table of only real errors, metadata gaps, and missing transcripts, with GitHub links to jump straight to each file. This is the "what needs fixing" list.
** *Warnings* — every warning the pipeline auto-fixed, per conversation. Informational, not actionable.

[source,bash]
----
python generate_validation_report.py
----

Run it again (and commit the regenerated pages) after reprocessing a module — or via `sync.py`, which calls this automatically — to keep them current. With no arguments it discovers every module next to the `tools` checkout (or in a sibling `moduli/` folder); pass `--modules <dir> ...` to choose.

[[summarize]]
== `summarize.py`

Writes statistical summaries of a module into the summaries repository (`KIParla-summaries`, one folder per module), as a basis for data analysis. They are kept out of the module repositories. Everything is computed from `tsv/*.vert.tsv`, so the summaries can be regenerated at any time without reprocessing the EAF files. It is a separate step: run it after `sync.py` or `cli.py process`, and commit the result with the module.

[source,bash]
----
python summarize.py --output-dir <summaries_dir> <module_dir> [<module_dir> ...] [--code CODE ...]
python summarize.py --output-dir <summaries_dir> <module_dir> [<module_dir> ...] --check
----

`--check` writes nothing; it lists summaries that are missing or older than their `tsv/` file (each summary records the SHA-256 of its vertical) and exits with status 1 if there are any.

*Files*

* `<Module>/<code>.json` — one conversation: its `metadata`, `time`, `units`, `tokens`, `rates`, `annotated_overlaps`, `variation`, one entry per speaker under `speakers`, and the pipeline's own report (`WARNINGS`, `ERRORS`, `AUDIO_CHECK`, …) under `pipeline` when `tmp/process/json/<code>.json` exists.
* `<Module>/snapshot.json` — the whole module: `totals`, `by_conversation_type`, and three flat tables ready for pandas: `conversations`, `participants` (one row per person, across conversations) and `speakers_in_conversations` (one row per speaker in each conversation).

[source,python]
----
import json, pandas as pd
snap = json.load(open("KIParla-summaries/KIP/snapshot.json"))
rows = pd.json_normalize(snap["speakers_in_conversations"])
people = rows[rows["in_participants_metadata"]]
----

*Definitions*

* *tokens* are all rows of the vertical; *linguistic tokens* those whose `type` is `linguistic` (words). The other types (`shortpause`, `nonverbalbehavior`, `unknown`, `anonymized`, `error`, `warning`) are counted in `tokens_by_type`.
* A *unit* is a transcription unit; its interval runs from the `Begin=` of its first token to the `End=` of its last.
* *Speech seconds* of a speaker are the time during which they have at least one unit active (the union of their units, so overlapping units of the same speaker are not counted twice). `share_of_speech_time` is relative to the sum of all speakers' speech seconds.
* *Rates*: `tokens_per_second` and `linguistic_tokens_per_second` divide by the speaker's own speech seconds (conversation level: by the conversation's speech seconds); `linguistic_tokens_per_minute` is the same figure per minute.
* *Overlap seconds* are the time during which at least two different speakers are active, computed from unit intervals regardless of how the transcribers marked overlaps; `share_overlap_of_speech` divides by the conversation's speech seconds. For a speaker, `share_of_own_speech_overlapped` is the part of their speech during which someone else was also speaking.
* *Annotated overlaps* are tokens carrying an `overlaps` annotation, i.e. spans transcribers bracketed. `events` counts distinct matched events; `unmatched_spans` counts annotated spans for which the pipeline found no time overlap (`(?)` in the vertical). Shares are relative to linguistic tokens.
* A *turn* is a maximal run of consecutive units, in time order, by the same speaker.
* `silence_seconds` is the conversation span (first `Begin` to last `End`) minus speech seconds; `metadata_duration_seconds` is `duration` from `conversations.tsv` for comparison.
* `in_participants_metadata` is `false` for tiers not listed in `participants.tsv` (unidentified speakers written `???`, and `environment`); filter on it for per-person figures.
* `with_lemma` and `with_upos` count annotated tokens, so the same snapshot will show progress once lemmatization is added.

[[build_explorer]]
== `build_explorer.py`

Builds the *corpus explorer*, a small static site (`index.html`, `explorer.css`, `core.js`, `app.js`, `data.json`) for browsing KIParla and assembling a sub-corpus. It reads only the `<Module>/snapshot.json` of each module in the summaries repository (see <<summarize>>), so run `summarize.py` first; it needs no module repositories.

[source,bash]
----
python build_explorer.py --summaries KIParla-summaries \
    --modules KIP KIPasti ParlaBO ParlaTO ParlaBZ Stra-ParlaBO Stra-ParlaTO \
    --output-dir KIParla-artifacts/explorer \
    [--artifacts-url URL] [--single-file kiparla-explorer.html] [--zip kiparla-explorer.zip]
----

`--modules` takes module names, and their order matters for a conversation present in more than one module (KIP and ParlaTO share 16): it is listed once, under the first module, and the others are recorded in `modules`. In production (any static host, e.g. GitHub Pages) the page fetches `data.json` (about 650 KiB) when it loads, so the data can be cached and updated without touching the code, and the same file is the dataset for analysis outside the page. A page opened from disk cannot fetch, and sibling files can get lost or blocked when a folder is sent around, so `--single-file` writes one self-contained `index.html` with the styles, scripts and data inline (about 700 KiB), and `--zip` writes that file in a zip. Use these to send the explorer to someone. `--artifacts-url` is where the transcription pages are (default: the published KIParla-artifacts site, so links work wherever the folder is; use `../` for a sibling checkout).

*What the page does*

* *Filters*: conversation metadata (module, type, subtype, year, collection point, languages), speaker attributes (gender, age range, occupation, study level, region, mother tongue; match "at least one speaker" or "every speaker") and measured features (duration, overlap by time and by annotated tokens, speech rate, tokens, ...), each with a histogram and a range. Facet counts show what each option would select given the other filters, and values can be "unknown".
* *Overview*: totals, shares and rate of the selection next to the whole corpus, what it is made of (conversations and distinct speakers per category), per-feature minimum, median, mean and maximum, and a distribution plot.
* *Explore*: a scatter plot of any two features, coloured by a metadata field. Drag a rectangle to turn it into two range filters.
* *Conversations*: the selected conversations with links to their transcriptions; any can be taken out by hand.
* *Export*: the list of codes, a CSV with all features, a JSON with the filters and module versions, and a `bash` script that copies the chosen formats (vertical, ELAN, linear, summary, HTML, PDF) from local checkouts into one folder.

The selection is kept in the URL (`#s=...&t=<tab>`), so a sub-corpus can be shared as a link. Speaker figures count only identified speakers (see `in_participants_metadata` in <<summarize>>).

*Sources*, in `explorer/`: `template.html` (markup, becomes `index.html`), `explorer.css`, `app.js` (the interface) and `core.js` (filtering and statistics, no DOM). The core is tested under Node (`tests/explorer_core.test.js`, also run by `pytest` when `node` is available). Rebuild the site whenever summaries change and commit the result.

[[sync]]
== `sync.py`

One-shot, one-directional sync for a single edited file. Run manually after opening/saving a `.eaf` in ELAN, or hand-editing a `.vert.tsv`:

[source,bash]
----
python sync.py --from-eaf <path/to/X.eaf>
python sync.py --from-vert <path/to/X.vert.tsv>
----

`--from-eaf` chains `eaf2csv` → `process` (updates `tsv/`, `translations/`, `tmp/process/`) → `tsv2formats` → `check_participants` → `generate_validation_report`.

`--from-vert` chains `vert2eaf` (overwrites `eaf/X.eaf` in place) → `tsv2formats` → `check_participants` → `generate_validation_report`. Pipeline warnings/errors in the report are not refreshed in this direction — that would mean reprocessing the freshly-written eaf, which is exactly the reverse-direction auto-trigger this command avoids, so the two commands never ping-pong off each other.

Module is inferred from the file's path; pass `--module` to override.

== Design note

These scripts are intentionally lightweight and file-oriented.
When behavior becomes complex enough to need a richer data model or reusable pipeline code, it lives in a dedicated module instead.

`normalize.py` is the first such module in this repository: it provides the validation and normalization pipeline for transcription unit text.
See xref:normalize.adoc[Normalization pipeline] for details.
